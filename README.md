# 🍪 Cookie 发送决策实验室

用 Node.js + Express + 原生前端（无框架）实现的 **Cookie 发送决策教学模拟器**。

你可以在页面上编辑一串**按时间推进的步骤**，每一步填写：

- **递增秒数**：距上一步经过多少秒（模拟时钟会累加，用于判断 Max-Age 过期）
- **请求 URL / 方法**
- **顶层页面 URL**（地址栏中的站点，用于判断同站；留空表示一方请求）
- **顶层导航标记**（该请求是不是顶层导航，例如点击外链跳转）
- **Set-Cookie 列表**：响应里逐行写入的 `Set-Cookie` 内容

执行顺序严格按照浏览器模型：**每一步先判定发送哪些 Cookie，再应用响应中的 Set-Cookie**。
页面会逐步列出：

1. 本请求实际发出的 `Cookie:` 头与逐项 Cookie；
2. 没有发送的 Cookie 及**全部命中原因**（域、路径、过期、HTTPS、SameSite）；
3. 每条 Set-Cookie 的处理结果（新写入 / 覆盖更新 / 删除 / 拒绝写入及原因）；
4. 该步结束后的 Cookie Jar 快照。

每个有效请求还会给出**服务端同名取值**分析（取首项 / 取末项两种口径与同名组明细），
结果时间线顶部另有**分歧时间线**汇总（详见下文）。

在以上任意一种 Cookie 行尾点击 **🕰 生命周期**，还可以打开该 Cookie 的**生命周期轨迹**（详见下文）。

## 快速开始（Docker）

```bash
docker compose up --build
```

然后用浏览器打开：

```
http://localhost:3000
```

停止：`Ctrl+C`，或在另一终端执行 `docker compose down`。

## 不用 Docker，直接本地运行

需要 Node.js 18+：

```bash
npm install
npm start
# 打开 http://localhost:3000
```

自检（核心规则断言，含公共后缀/私有后缀边界回归）：

```bash
npm test
```

更新内置的公共后缀列表（需要联网；列表本身随仓库内置，运行时离线）：

```bash
npm run update-psl
```

## 页面使用

- **▶ 运行模拟**：按当前编辑的步骤顺序执行；
- **载入示例**：内置三个示例，覆盖完整生命周期、SameSite 三种模式、Set-Cookie 拦截/路径/有效期；
- **🎯 最小复现**：在结果时间线中，每个已发送 / 未发送的 Cookie 行尾都有“最小复现”按钮，
  点击后自动把当前步骤缩减为**以该步为结尾、仍能复现该 Cookie 结果**的最小序列（详见下节）；
- **🕰 生命周期**：从任一步的**已发送 / 未发送 Cookie、成功解析的响应处理项或步末 Jar**
  中选择一项，追踪截至该步、同一标识的状态变化（详见下节）；
- **🧭 策略求解**：在第 ② 部分选择一条**成功写入**的 Set-Cookie，标记其后的请求上
  该项应发送 / 不应发送，反向求解满足全部标记的 Domain / Path / Secure / SameSite
  组合（详见下节）；
- **🔀 服务端同名取值**：每个有效请求卡片内按实际 `Cookie:` 头顺序分析同名取值，
  结果时间线顶部汇总每个名称的分歧何时产生、何时消失（详见下节）；
- 步骤可任意新增、删除，Set-Cookie 每行一条（不要写 `Set-Cookie:` 前缀）。

## 最小复现（🎯）

在调试“为什么这个 Cookie 被（或不）发送”时，结果列表里的每个已发送 / 未发送 Cookie
都可以被选为**目标**，一键生成最小复现序列：

- **目标标识**：名称 + 值 + 域 + 路径 + 发送状态；未发送目标还要求**原因集合**完全一致
  （例如必须仍是 `SAMESITE_STRICT` 而不只是“没发送”）。
- **结尾固定**：生成的序列以目标所在步为结尾，该步之后的步骤直接截掉；
  目标请求的 **URL、方法、顶层页面 URL、导航标记保持不变**。
- **只允许两类删减**：
  1. 删除目标步之前的**整步**——被删步的经过秒数会**并入下一保留步**，
     因此所有保留请求的绝对时刻（模拟时钟）不变，Max-Age / Expires 判定不受影响；
  2. 删除截至目标步（含目标步）的任意一行 **Set-Cookie**。
- **逐项核对**：每次删减都重跑模拟引擎，确认末步仍能复现目标才接受；
  反复尝试直至**任何单项再删都会改变目标结果**（1-minimal）。
- **预览与载入**：面板显示缩减前后的步数与 Set-Cookie 行数及逐步预览；
  点击“载入到编辑器”才会替换当前步骤，预览本身不改动编辑内容。
- **无法定位目标**（例如步骤已修改但未重新运行）：只给出提示，当前编辑内容不变。

## 生命周期轨迹（🕰）

在结果时间线中，可以从任一步的以下四类位置选择一项：

- **① 判定发送**中的已发送项；
- 未发送列表中的项（含因过期出现在未发送列表、随后才被淘汰的 Cookie）；
- **② 应用 Set-Cookie 响应**中的**成功解析项**（新写入 / 覆盖 / 删除，含未命中的删除）；
  被拒绝的写入不属于任何轨迹，行内只显示提示；
- 步末 **Cookie Jar 快照**中的任一项。

追踪的唯一标识与 Jar 键一致：**名称（不区分大小写）+ 规范化域（去掉前导点）+ 路径**。
因此同名但域或路径不同的 Cookie **分开追踪**；用 Unicode / punycode 两种写法指向的同一域也会归入同一条轨迹。

轨迹**严格按执行顺序**列出截至该步的全部状态变更，每条记录标明：

- 所在步骤与**绝对时刻**（模拟时钟 ISO 时间）；
- 对应的 **Set-Cookie 原文**（过期淘汰是引擎内部事件，标注为无原文）；
- 事件类型：**写入 / 覆盖 / 删除 / 过期淘汰**；
- **变更前 / 变更后值**（值、host-only / Domain、Path、Secure、SameSite、到期时间）；
- 事件后的**存活状态**（存活至何时 / 会话期 / 已删除 / 已过期淘汰）。

细节语义与模拟结果完全一致：

- **覆盖**沿用同一个（名称、域、路径）键，并以覆盖时刻**重算到期时间**；
- **未命中的删除**仍显示为一条删除事件，标注“空操作：未命中任何项，轨迹不变”；
- **被拒写入**不产生任何事件，不改变轨迹；
- **过期 Cookie** 在**首次到期后的有效请求中仍进入未发送判定**（未发送列表与轨迹原因一致），
  完成判定后才从 Jar **淘汰**——轨迹事件由同一个发送决策引擎产出，不做二次推算；
- 轨迹只包含**截至所选步**（含）的事件；每条事件可一键 **↩ 跳回原步骤**（滚动并高亮对应结果卡片）；
- **关闭视图不改动任何编辑内容**，重新运行模拟时轨迹面板随结果一起刷新。

## 策略求解（🧭）

在结果时间线第 ② 部分中，每条**成功写入**（新写入 / 覆盖更新）的 Set-Cookie 行尾
都有“🧭 策略求解”按钮，用于反向求解：“该 Cookie 需要什么样的作用域属性，才能在
其后的请求上按期望发送 / 不发送”。

- **目标**：仅限成功写入（新写入 / 覆盖更新）的 Set-Cookie；删除项与被拒写入的条目
  不可作为目标；
- **标记**：在写入步之后的**有效请求**（URL 非法被跳过的步骤除外）中任选 **至多 8 步**，
  分别标记该项**应发送**或**不应发送**；
- **保持不变**：步骤、名称、值、有效期（Max-Age / Expires）与其他属性
  （HttpOnly、未知属性等按原文保留）；
- **只枚举四个属性**：
  - **Domain**：host-only，以及来源主机与其合法父域的 `Domain=` 形式（从窄到宽）；
  - **Path**：`/`、原路径、各标记请求路径的逐级前缀（`/a/b/c` → `/a`、`/a/b`、`/a/b/c`）；
  - **SameSite**：Strict / Lax / None；**Secure**：有 / 无；
  - 每个候选都先通过现有的写入校验（Domain 匹配、公共后缀、`SameSite=None` 必须
    `Secure` 等），不合法的组合直接排除；
- **核对**：把候选替换进原响应行并**重跑完整序列**，按候选的名称、值、域、路径
  逐一核对各标记步的实际发送状态；
- **取首解**：多解时按 host-only → Domain 从窄到宽 → Path 从长到短（同长按字典序）→
  SameSite Strict/Lax/None → Secure 有/无 的顺序，取第一个满足全部标记的候选；
- **结果**：展示可一键复制的 Set-Cookie 行、解的四属性，以及逐步核对表
  （期望 / 实际 / 未发送原因）；**无解时只给出提示**。
  求解过程不改动任何编辑内容，需要时可复制解手动替换原响应行。

## 服务端同名取值（🔀）

同名 Cookie（名称相同、域或路径不同）会并列出现在同一个 `Cookie:` 头中，而服务端
框架对同名项的解析口径不一：有的取**首项**，有的取**末项**。本分析把这两种口径都
算出来，并沿时间线追踪分歧的来龙去脉。

**逐请求分析**（每个有效请求卡片内，位于 ① 判定发送与 ② 应用响应之间）：

- 按本请求**实际 `Cookie:` 头顺序**、名称**区分大小写**分组（`sid` 与 `SID` 是两个名称）；
- 每个名称分别给出服务端**取首项**与**取末项**时读到的值；
- 同名组逐项列出头中每项的值，以及对应已发送 Cookie 的**域、路径和创建次序**；
- 两种取值不同时标出**分歧**；同名但首末一致只标注“首末一致”；
- **空头**（本请求不发送任何 Cookie）时显示明确状态，不显示空表。

**分歧时间线**（结果时间线顶部的汇总卡片）：

- 沿**有效请求**（URL 非法被跳过的步骤不算）标出每个名称的分歧**何时产生、何时消失**
  （仅剩一项 / 该名称不再发送 / 首末转为一致）；
- 每次转变都按 **Jar 键中的名称**（不区分大小写，与 `CookieJar.keyOf` 一致）关联
  相邻步骤里的**写入 / 覆盖 / 删除 / 过期淘汰**事件，每条事件可 ↩ 跳回原步骤；
- 因果窗口严格遵循执行顺序：**同一步先发送后处理响应**，本步响应中的写入 / 覆盖 /
  删除只影响后续请求，不会计入本步取值的关联事件；过期淘汰发生在本步发送判定中，
  影响本步（含）之后的请求；
- 没有有效请求、全部请求空头、或全程无分歧时都显示明确状态；
- 分析由模拟结果纯推导（`public/serverview.js`，前端与测试共用），**重新运行即刷新，
  不改动任何编辑内容**。

## 模拟的规则

### 存储（Set-Cookie）

- 同名 Cookie 按 **名称 + 域 + 路径** 分别保存（同名不同域/路径共存）；再次命中同一键则覆盖更新。
- **缺省 Path = `/`**；**缺省 SameSite = `Lax`**。
- `Max-Age` 优先于 `Expires`；`Max-Age=0`（或负数、已过期的 Expires）立即删除对应键。
- 未指定 `Domain` 时为 **Host-Only** Cookie，只回送给设置它的那台主机；
  指定 `Domain`（自动去掉前导点）时可回送该域及其子域。
- `Domain` 必须**等于响应主机或为其父域**，否则拒绝（`Domain` 不匹配）。
- `Domain` **不能是公共后缀**，否则拒绝。公共后缀使用**完整离线 Mozilla Public Suffix List**
  （ICANN + PRIVATE DOMAINS 两段），既包含 `com`、`co.uk` 这类通用后缀，也包含
  `s3.amazonaws.com`、`github.io` 这类**私有后缀**——所以
  `sid=1; Domain=s3.amazonaws.com` 会被拒绝，避免 `alice.s3.amazonaws.com` 写入的
  Cookie 泄漏给 `bob.s3.amazonaws.com`。规则按例外优先、最长匹配处理（通配规则如
  `*.ck`、例外规则如 `!www.ck`）。国际化域名规则（如 `公司.cn`）与主机统一按
  ASCII（punycode）表示匹配，因此 `sid=1; Domain=xn--55qx5d.cn` 同样以公共后缀拒绝。
- **`SameSite=None` 必须同时带 `Secure`**，否则拒绝。
- 会话期 Cookie（没有 Max-Age / Expires）在模拟期间一直保留，直到被删除；时间只用于持久 Cookie 的过期判断。

### 同站判断（schemeful site）

- 同站 = **协议相同**（http/https）且**可注册域相同**（eTLD+1，由内置的**完整离线
  公共后缀列表**计算，涵盖私有后缀）。
- 端口不参与同站判断；IP 地址与单标签主机名（如 `localhost`）按整台主机比较。
- 因此 `http://a.example.com` 与 `https://example.com` 是**跨站**（协议不同），
  `https://shop.example.co.uk` 与 `https://ads.co.uk` 也是**跨站**（可注册域不同），
  `https://alice.s3.amazonaws.com` 与 `https://bob.s3.amazonaws.com` 同样**跨站**
  （`s3.amazonaws.com` 是私有后缀，两个桶各自是独立可注册域）。

### 发送（Cookie 请求头）

对 Jar 中每一项依次检查（可能同时命中多个未发送原因）：

| 检查 | 不满足时 |
| --- | --- |
| **域** | Host-Only 要求主机完全相等；Domain Cookie 要求主机为该域或其子域 |
| **路径边界** | 请求路径等于 Cookie Path，或以其为前缀且下一个字符是 `/`（或 Path 本身以 `/` 结尾） |
| **HTTPS** | `Secure` Cookie 不能经 `http://` 发送 |
| **过期时间** | 持久 Cookie 当前时钟超过 Max-Age/Expires 即不发送并从 Jar 淘汰 |
| **SameSite=Strict** | 仅同站发送，跨站一律不带 |
| **SameSite=Lax** | 同站发送；跨站只允许**顶层导航 + 安全方法**（GET/HEAD/OPTIONS/TRACE） |
| **SameSite=None** | 允许跨站（写入时已强制 Secure） |

发送项按 RFC 6265 排序：**路径更长者优先，其次写入更早者优先**，拼成 `Cookie: a=1; b=2`。

### 内置示例速览

- **示例 1（完整流程）**：在 `shop.example.com` 写入 Domain Cookie、Host-Only Cookie 与 `SameSite=None` Cookie → 子域 API 同站请求 → sid 过期被淘汰 → 跨站 POST 到 `ads.net`（Strict/Lax 不带、None 因域不同也不带）→ 从商店页面点击外链**顶层 GET 导航**到 `ads.net`（ads.net 自己的 Lax Cookie 放行）→ 回到商店覆盖更新并删除 → 验证删除结果。
- **示例 2（SameSite）**：一次登录写入 Strict/Lax/None 三个 Cookie，随后依次观察跨站顶层 GET、跨站 POST、跨站子资源、同站请求，以及 `https → http` 降级被当作跨站。
- **示例 3（拦截/路径/有效期）**：Domain 不匹配、公共后缀、None 缺 Secure 被拒绝；同名不同路径分别保存；路径边界 `/admin` vs `/adminx`；Secure 不走 HTTP；Max-Age 到期淘汰。

## 说明与取舍

- 公共后缀使用**随仓库内置的完整 Mozilla PSL**（`data/public_suffix_list.dat`，
  ICANN 段与 PRIVATE 段都加载），运行时完全离线、不发网络请求；Cookie 写入校验与
  同站判断共用同一份规则。匹配按官方算法：**例外规则优先**、其次**最长匹配**
  （精确规则先于同层通配规则）、未命中再由隐式 `*` 兜底。可用
  `npm run update-psl` 更新到最新列表。
- **国际化域名（IDN）统一为 ASCII 表示**：列表中以 Unicode 书写的规则（精确、通配、
  例外三种形式，如 `公司.cn`）在加载时转换为 punycode（`xn--55qx5d.cn`）；URL 主机与
  Cookie `Domain` 无论写成 Unicode 还是 Punycode，也都归一化为同一 ASCII 表示后再
  校验、保存与匹配，可注册域与同站计算同样基于该表示。因此
  `https://alice.公司.cn/` 与 `https://bob.公司.cn/` 被判为**跨站**。
- 例外保留：`localhost` 等 RFC 6761 单标签特殊用途名**不**当作公共后缀，方便本地开发；
  IP 地址（含 IPv6）与单标签主机名不做 eTLD+1 计算，按整台主机作为“站”。
- 同站采用 **schemeful same-site**（Chrome 当前模型）：协议不同即跨站。
- HttpOnly 属性会解析但不参与决策（模拟器不区分 document.cookie 与网络请求）。
- 顶层页面 URL 留空时按一方（同站）请求处理；填了但无法解析时按跨站处理并给出警告。
